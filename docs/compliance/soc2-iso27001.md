# Correspondance SOC 2 et ISO/IEC 27001

*Comment s'appuyer sur les preuves produites par Thot Secure pour documenter ses propres contrôles dans une démarche SOC 2 ou ISO/IEC 27001 — et ce qui reste, sans exception, à la charge de l'exploitant.*

!!! warning "Ni certification, ni audit, ni attestation"
    **Thot Secure n'est certifié SOC 2 ni ISO/IEC 27001. Aucun organisme n'a certifié ce logiciel.**
    Cette page n'est **pas** un rapport d'audit, **pas** une attestation, **pas** une opinion d'auditeur
    et **pas** une déclaration de conformité. C'est une **aide à la documentation** : elle indique
    quelles preuves le produit peut fournir, et pour quel contrôle elles peuvent servir de pièce.
    La conformité, la définition du périmètre, la mise en œuvre des contrôles manquants, l'obtention
    d'un rapport SOC 2 ou d'un certificat ISO/IEC 27001 relèvent entièrement de l'exploitant, avec
    son auditeur. Rien ici ne remplace un audit ni un avis juridique.

Référence technique de tout ce qui suit : [`../architecture/api-contract.md`](../architecture/api-contract.md)
(contrat gelé v0.1.0 — §1 invariants, §3 schémas, §4 routes et capacités, §6 garde-fous, §9 variables,
§10 sécurité produit, §11 tests attendus).

## 1. Vocabulaire, pour éviter les confusions

| Terme | Ce que c'est | Ce que ce n'est pas |
|---|---|---|
| **SOC 2** | Un **rapport d'attestation** d'un auditeur indépendant, portant sur les *Trust Services Criteria* (TSC) du cadre AICPA, pour une organisation et une période données | Un certificat ; un label produit ; une preuve de conformité au RGPD |
| **TSC — Sécurité (catégorie commune, « CC »)** | Les critères communs : contrôle d'accès, opérations, gestion du changement, atténuation des risques | — |
| **TSC — catégories additionnelles** | Disponibilité, intégrité du traitement, confidentialité, vie privée : **facultatives**, à inclure explicitement dans le périmètre | Un choix implicite : ce qui n'est pas dans le périmètre n'est pas attesté |
| **SOC 2 Type I** | Description des contrôles et de leur **conception** à une date donnée | Une preuve d'efficacité dans la durée |
| **SOC 2 Type II** | Conception **et efficacité opérationnelle** sur une **période d'observation** | Un instantané : la période se choisit et s'assume |
| **ISO/IEC 27001** | Un **système de management de la sécurité de l'information (SMSI)** : gouvernance, analyse de risques, amélioration continue, plus les mesures de l'Annexe A | Une liste de courses techniques ; un contrôle produit |
| **ISO/IEC 27001:2013 vs 2022** | Deux révisions, avec deux numérotations d'Annexe A (A.12 en 2013, A.5/A.8 en 2022) | Des référentiels interchangeables : la correspondance entre versions n'est pas un simple renommage |

!!! danger "Le logiciel est un outil, pas un SMSI"
    Aucune fonctionnalité d'Thot Secure ne peut tenir lieu de politique de sécurité, d'analyse de
    risques, de sensibilisation du personnel ou d'engagement de la direction. Un outil de détection
    et de réponse fournit des **preuves techniques** ; un SMSI est un **système de management**. La
    confusion entre les deux est la première cause d'échec en audit.

## 3. Correspondance ISO/IEC 27001

    **A.12** appartient à la révision **ISO/IEC 27001:2013** ; **A.5 et A.8** à la révision

## 4. Preuves fournies par le produit

### 4.1 Journal d'audit chaîné

`AuditRecord` (§3.5) porte `seq`, `ts`, `tenant_id`, `actor`, `actor_role`, `action`, `target`,
`before`, `after`, `prev_hash`, `hash`, avec
`hash = sha256(seq|ts|tenant_id|actor|actor_role|action|canonical(target)|canonical(before)|canonical(after)|prev_hash)`.
Le journal est **append-only** et le genesis a `prev_hash = "sha256:genesis"`.

| Besoin d'audit | Route ou commande |
|---|---|
| Lister et filtrer les actions | `GET /api/v1/audit?since=…&until=…&action=…&actor=…` (capacité `read:audit`) |
| Démontrer l'intégrité | `GET /api/v1/audit/verify` → `{"valid":true,"records":n,"broken_at":null}` |
| Exporter vers un SIEM | `GET /api/v1/audit/export?format=jsonl\|cef` |
| Vérifier côté exploitation | `thotsecure audit verify`, `thotsecure audit tail` (code de sortie `3` si la chaîne est cassée) |

```bash
# Échantillon d'audit pour un auditeur : les approbations de la période sous revue
curl -sS "$AO_URL/api/v1/audit?action=action.approve&since=2026-01-01T00:00:00Z" \
  -H "X-API-Key: $AO_AUDITOR_KEY" | python -m json.tool

# Preuve d'intégrité : rejouer la vérification de la chaîne
curl -sS "$AO_URL/api/v1/audit/verify" -H "X-API-Key: $AO_AUDITOR_KEY"
# → {"valid":true,"records":18432,"broken_at":null}
```

Valeur probante : chaque décision référence un `policy_id` et chaque action porte un `audit_seq`
(§10), ce qui permet de relier une contre-mesure à la politique qui l'a produite et à la trace
d'audit correspondante. Les champs `before`/`after` documentent la transition d'état, ce qui rend la
séquence vérifiable pas à pas.

| `viewer` | `read:events read:findings read:rules read:policies read:audit read:stats` |
| `analyst` | viewer + `write:events write:findings` |
| `responder` | analyst + `execute:actions approve:actions` |
| `admin` | responder + `admin:tenants admin:rules admin:keys admin:policies` |

Le RBAC est appliqué par dépendance FastAPI **et** vérifié dans le core (`capabilities`), ce qui
signifie qu'une route mal câblée ne suffit pas à ouvrir un accès (§10). `GET /api/v1/auth/whoami`
renvoie le tenant, le rôle, les capacités et le mode d'autonomie : c'est la preuve d'attribution
d'un accès, directement exploitable dans un dossier de contrôle.

### 4.3 Revue d'accès et révocation

| Étape de revue | Moyen |
|---|---|
| Inventorier les accès | `GET /api/v1/tenants/{id}/keys` → `key_id`, `label`, `role`, `created_at`, `last_used_at`, `revoked_at` |
| Repérer les clés dormantes | `last_used_at` ancien ou nul |
| Repérer les excès de privilège | `role` supérieur au besoin réel (clé `admin` sur un collecteur) |
| Révoquer | `DELETE /api/v1/keys/{key_id}` → `204` (immédiat) ou `thotsecure key revoke --key-id <id>` |
| **Rotation** | Le contrat ne décrit **aucune** route de rotation : la rotation se pratique en **créant une nouvelle clé** (`POST /tenants/{id}/keys`) puis en **révoquant l'ancienne**. Documentez cette procédure comme telle |

```bash
# Revue d'accès trimestrielle : inventaire complet des clés du tenant
curl -sS "$AO_URL/api/v1/tenants/acme/keys" -H "X-API-Key: $AO_ADMIN_KEY" | python -m json.tool

# Rotation : nouvelle clé (affichée une seule fois), puis révocation de l'ancienne
curl -sS -X POST "$AO_URL/api/v1/tenants/acme/keys" -H "X-API-Key: $AO_ADMIN_KEY" \
  -H 'Content-Type: application/json' -d '{"role":"responder","label":"ci-2026Q3"}'
curl -sS -X DELETE "$AO_URL/api/v1/keys/01J8Z…" -H "X-API-Key: $AO_ADMIN_KEY" -o /dev/null -w '%{http_code}\n'
# → 204
```

### 4.4 Gestion des changements

Règles, politiques et playbooks sont du **YAML versionnable** (§5, §6, §7) : la modification d'un
comportement de détection ou de décision est un **changement de code**, avec revue et historique Git.

| Élément | Moyen de preuve |
|---|---|
| Validation avant application | `POST /api/v1/rules/validate` (capacité `admin:rules`) → `{"valid":true,"errors":[]}` ; CLI `thotsecure rules validate [--path rules]`, `thotsecure policies validate` |
| Application explicite | `POST /api/v1/rules/reload` → `{"loaded":n,"errors":[…]}` ; `POST /api/v1/policies/reload` — la recharge est **manuelle**, jamais implicite |
| Traçabilité | Historique Git du dépôt de règles/politiques/playbooks + entrée d'audit de l'opération de rechargement |
| Effet attendu | Une règle invalide est **rejetée avec un diagnostic** sans casser le chargement des autres (§5) : un changement défectueux ne provoque pas de panne silencieuse de la détection |

!!! note "Périmètre de cette sous-section"
    Le contrat décrit la validation et la recharge, donc la **preuve de changement contrôlé**. Le
    détail du pipeline d'intégration continue (déclencheurs, environnement, approbations,
    artefacts) appartient à un autre lot documentaire : il n'est **pas** décrit ici et ne doit pas
    être supposé. De même, le contrat documente la recharge des règles et des politiques, **pas**
    celle des playbooks (`THOT_PLAYBOOKS_DIR`, §9) : vérifiez ce point contre le contrat avant
    de l'affirmer dans un dossier d'audit.

### 4.5 Journalisation et rétention

| Réglage | Effet | Usage en audit |
|---|---|---|
| `THOT_LOG_FORMAT` | `json` (défaut) ou `console` | Le format `json` est directement exploitable par un collecteur de journaux |
| `THOT_LOG_LEVEL` | `INFO` par défaut, jusqu'à `DEBUG` | Prouver la granularité retenue et la maîtriser (le `DEBUG` prolongé n'est pas un état de production sain) |
| Export SIEM | `GET /api/v1/audit/export?format=cef\|jsonl` | Preuve de centralisation ; le destinataire devient un sous-traitant à encadrer |
| `THOT_RETENTION_DAYS` | Purge des **événements**, défaut `30` | Prouver que la rétention est bornée, justifiée et documentée (§6 de [`rgpd.md`](rgpd.md)) |
| Délégation des secrets | `THOT_SECRET_KEY` (*pepper* + signature) | Prouver que la valeur n'est pas un défaut de développement et qu'elle est gérée hors du dépôt |

```json
{
  "ts": "2026-02-14T10:00:02.331Z",
  "level": "INFO",
  "logger": "thotsecure.api.audit",
  "msg": "audit.verify.ok",
  "tenant_id": "acme",
  "records": 18432,
  "broken_at": null
}
```

### 4.6 Sauvegarde, restauration et réversibilité

| Preuve | Contenu attendu |
|---|---|
| Sauvegarde chiffrée | Sauvegarde de la base (`THOT_DB_URL`, §9) et des répertoires de règles/politiques/playbooks, chiffrée, avec horodatage et emplacement |
| Test de restauration daté | Restauration sur un environnement isolé, vérification `GET /readyz` → `200`, puis `GET /api/v1/audit/verify` pour confirmer l'intégrité de la chaîne restaurée |
| Réversibilité des actions | `POST /api/v1/actions/{id}/rollback` exécuté avec succès (§1 invariant 3), statut `rolled_back`, entrée d'audit correspondante |
| Idempotence | `idempotency_key` (§3.4) : la réexécution ne produit pas de double effet |

!!! warning "Une sauvegarde non testée n'est pas une preuve"
    La restauration et la vérification de la chaîne d'audit **après** restauration forment la preuve
    attendue. Sans elles, vous démontrez l'existence d'un fichier, pas la capacité de reprise.

### 4.7 Moindre privilège en pratique

| Pratique | Justification d'audit |
|---|---|
| Une clé par usage (collecteur, CI, exploitation, audit, console) | Limite le rayon d'action d'une clé compromise et rend l'audit lisible par `actor` |
| Un rôle par besoin réel | Un collecteur n'a besoin que de `write:events` (`analyst`) ; un auditeur de `viewer` |
| Aucune clé `admin` dans un collecteur ou un script de CI | `admin` cumule `admin:tenants`, `admin:keys`, `admin:rules`, `admin:policies` : c'est un compte à privilèges |
| Libellés de clés fonctionnels et non nominatifs | Un libellé nominatif transforme un identifiant technique en donnée personnelle (voir [`rgpd.md`](rgpd.md) §3) |
| `THOT_BOOTSTRAP_API_KEY` changée dès l'installation | Clé admin initiale connue publiquement (`thot_BOOTSTRAP_changemebeforefirstuse`, §9) : sa persistance est une non-conformité immédiate |

### 4.8 Rapports et artefacts

`GET /api/v1/findings/{id}/report?format=md|html|json|sarif` (§4.8) produit un artefact exploitable,
et `thotsecure report <finding_id> --format md|html|json|sarif -o out.md` fournit l'équivalent CLI. Le
format **SARIF 2.1.0** est directement consommable par GitHub Code Scanning : un finding de
dépendance ou de configuration peut donc apparaître comme **alerte de sécurité tracée** dans
l'historique du code, ce qui constitue une preuve de détection *et* de traitement.

## 5. Ce qui reste de la responsabilité du client

!!! danger "La part non délégable"
    Aucun contrôle de gouvernance, de gestion des personnes, de sécurité physique ou de gestion
    fournisseurs ne peut être satisfait par un logiciel. Ces éléments sont **exigés par l'auditeur**
    et relèvent de l'exploitant.

| Exigence d'audit classique | Fourni par Thot Secure | À produire par le client |
|---|---|---|
| Politique de sécurité de l'information | Rien | Politique signée par la direction, diffusée, revue |
| Analyse et traitement des risques | Rien | Méthodologie, registre des risques, plan de traitement, acceptation formelle |
| Sensibilisation et formation du personnel | Rien | Programme, preuves de participation, tests de phishing |
| Gestion des fournisseurs | Preuves techniques d'usage (exports, configuration) | Évaluation, contrats, DPA, revues périodiques |
| Sécurité physique | Rien | Contrôle d'accès aux locaux et aux salles, sauvegardes hors site |
| Ressources humaines | Rien | Vérifications avant embauche, clauses de confidentialité, procédure de départ |
| Contrats et conformité RGPD | [`rgpd.md`](rgpd.md) comme aide | DPA signés, registre des traitements, DPIA, information des personnes |
| Vulnérabilités **de son propre SI** | Détection sur les cibles déclarées uniquement (`probe` opt-in, allowlist) | Scan complet, gestion des correctifs des OS et applications, tests d'intrusion |
| Gestion des correctifs système | Collecte `dependency`, playbook `patch-dependency` (PR, pas de merge) | Application des mises à jour, fenêtres de maintenance, redémarrages |
| Sauvegardes et copies hors site | Compatible, mais non opéré par le produit | Politique de sauvegarde, stockage hors site, tests de restauration, RTO/RPO |
| Gestion des secrets | Hachage des clés API, `THOT_SECRET_KEY` | Coffre de secrets, rotation, séparation des rôles, coffre pour la clé de signature |
| Revue périodique des accès | Inventaire et révocation disponibles (`last_used_at`, `revoked_at`) | Exécution **planifiée**, comptes rendus, validation |
| Gestion des incidents **hors périmètre Thot Secure** | Détection et réponse sur les cibles déclarées | Astreinte, escalade, communication, post-mortem — voir [`../operations/runbook.md`](../operations/runbook.md) |
| Classification de l'information | Minimisation possible (pseudonymisation, restriction des `payload`) | Schéma de classification, marquage, règles de manipulation |
| Conformité réglementaire sectorielle | Rien | Applicabilité, déclarations, contrôles sectoriels |
| Obtention et suivi des audits | Preuves techniques, capacité `viewer` pour l'auditeur | Sélection de l'auditeur, périmètre, remédiation, suivi des recommandations |

## 6. Comment un auditeur peut vérifier

Mode d'emploi pratique, à remettre à l'auditeur avec une clé de rôle `viewer` **dédiée** et une clé
`admin` temporaire si l'échantillonnage l'exige.

| Vérification | Manipulation |
|---|---|
| Échantillonnage d'actions | Tirer un échantillon de `action.approve`, `action.execute`, `action.rollback` via `GET /api/v1/audit?action=…&since=…&until=…`, puis confronter chaque entrée à l'`Action` correspondante (`GET /api/v1/actions/{id}`, `audit_seq`, `approved_by`, `approved_at`) |
| Intégrité du journal | Rejouer `GET /api/v1/audit/verify` (ou `thotsecure audit verify`, code de sortie `3` si négatif) : l'auditeur ne fait pas confiance à un rapport, il **recalcule** la chaîne |
| Non-répudiation des décisions | Pour chaque action tracée, lire `policy_id`, puis comparer à la politique réellement chargée (`GET /api/v1/policies` inclut l'ordre de priorité) : la décision doit être explicable par la politique invoquée |
| Cloisonnement multi-tenant | Fournir deux clés de tenants distincts ; vérifier qu'une requête sur les données de l'autre tenant renvoie `404`/`403` et **jamais** de données. Rappel : l'isolation est un invariant (§1 invariant 4) vérifié par un test dédié (§11, `tests/test_api.py`) |
| Sûreté par défaut | Vérifier `dry_run` (`THOT_DRY_RUN`, `Tenant.dry_run`) et le mode d'autonomie (`THOT_AUTONOMY`, `GET /api/v1/auth/whoami`) : en configuration par défaut, **aucune action réelle** (§1 invariant 1) |
| Contrôle du silence | Vérifier qu'aucune politique `ignore` n'a été ajoutée sans justification : le silence total exige une politique `ignore` **explicite** (§6), donc une trace versionnée |
| Journalisation exploitable | Lire le journal applicatif en JSON (`THOT_LOG_FORMAT=json`) et vérifier que les journaux du service ne contiennent ni clé API ni donnée personnelle inutile |
| Preuve de révocation | Comparer `GET /api/v1/tenants/{id}/keys` (avec `revoked_at`) à une tentative d'utilisation d'une clé révoquée → `401` |
| Preuve de changement contrôlé | Rejouer `POST /api/v1/rules/validate` sur le YAML du dépôt, comparer l'historique Git au résultat de `POST /api/v1/rules/reload` |
| Réversibilité | Demander la trace d'un `rollback` réussi et le résultat associé (`Action.rollback.result`, statut `rolled_back`) |

```bash
# Les quatre commandes à remettre à un auditeur pour un premier passage
curl -sS "$AO_URL/api/v1/audit/verify"          -H "X-API-Key: $AO_AUDITOR_KEY"
curl -sS "$AO_URL/api/v1/audit?limit=50"        -H "X-API-Key: $AO_AUDITOR_KEY"
curl -sS "$AO_URL/api/v1/policies"              -H "X-API-Key: $AO_AUDITOR_KEY"
curl -sS "$AO_URL/api/v1/auth/whoami"           -H "X-API-Key: $AO_AUDITOR_KEY"
```

!!! tip "Deux clés de tenants distincts valent mieux qu'un long discours"
    Le test d'isolation est la vérification la plus convaincante du périmètre multi-tenant : il se
    démontre en direct, avec deux clés, en quelques secondes. Préparez-le (jeu de données de test,
    tenants `demo-a` / `demo-b`, `thotsecure demo --tenant demo`) plutôt que de le décrire.
